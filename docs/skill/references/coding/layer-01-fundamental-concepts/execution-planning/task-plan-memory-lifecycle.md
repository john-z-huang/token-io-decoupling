# Task Plan Memory Lifecycle

[English](task-plan-memory-lifecycle.md) | [简体中文](task-plan-memory-lifecycle_zh_cn.md)

This owner defines the shared task plan's creation, updates, access, and archive lifecycle. It applies by default to Coding work, with or without an Issue. It does not own planning methods, execution authorization, live parent scheduling state, or authoritative repository documentation.

## General rules

### Default task plan

Every current and future Coding route must consume this owner before implementation and throughout execution. An explicit request for a plan or a dedicated planning mode is unnecessary. Respect an explicit user prohibition on persistence or a higher-priority write restriction: record that exception and keep bounded planning in the authorized context; do not silently treat missing tools, uncertain permissions, or a failed write as an exception. If the user requires a persisted plan and a restriction prevents it, stop the dependent work and report the conflict.

For an Issue task, read the Issue and relevant discussion, compare its requirements with current project facts, and synthesize the proposed change before implementation. Without an Issue, use the user's stated problem and current project facts in the same way. Before the initial analysis is complete, a concise provisional plan may capture the goal, known facts, and unanswered questions; it must not claim an implementation direction is released. Persist the concrete plan before implementation or dependent dispatch, and confirm that the authorized write operation succeeded. Review the proposed plan in the authorized context before writing; a normal successful write does not by itself require an immediate full readback. New facts that affect a dependent action must be recorded before that action; batch other material facts for the next applicable plan boundary.

### Names, storage, and initial evidence

Reuse the user's designated active plan for the same task. Before choosing a new name, confirm whether the authorized backend uses shared global storage or legacy project-local storage. In shared global storage, both active and archived plans must include the same verified repository key: `global/token-io-decoupling/repos/<repository-id>/plans/PLAN-[short-english-summary]` and `global/token-io-decoupling/repos/<repository-id>/archive-plans/PLAN-[short-english-summary]`. Optionally include a verified Issue number; omit `.md` from logical Memory names. Never place a new global plan directly in shared `plans/` or `archive-plans/`, and never use a basename, branch, remote URL, or worktree path as the repository key.

For this storage mapping, the repository key is `git-v1-` followed by the hexadecimal SHA-256 of `b"token-io-decoupling:git-common-dir:v1\0" + os.fsencode(str(canonical_git_common_dir))`, where `\0` denotes one NUL byte. Resolve the actual checkout root and canonical absolute Git common directory using trusted local repository facts. The main checkout and its linked worktrees share that common directory and key; independent repositories and independent clones have separate keys, even with identical names or remotes. Moving the common directory changes the key: stop to reconcile the old mapping rather than silently abandoning or migrating its plans. Missing or ambiguous repository identity blocks the global path. This is a local repository identity, not a portable identifier across machines. Reusing an old common-directory path reuses its key; confirm ownership and reconcile existing history before accepting a newly created repository at that path.

With an explicitly retained project-local backend, use `plans/PLAN-[short-english-summary]` and `archive-plans/PLAN-[short-english-summary]`; the default physical root is `<project-root>/.serena/memories/`. That compatibility mode does not provide cross-worktree sharing. Follow the actual configured Memory root and mapping, including authorized data-directory overrides; do not create a second store or invent a global root. Once shared global storage is selected, unavailable identity, root, mapping, or permission blocks that path instead of silently falling back to project-local storage. For a user-designated name, establish its corresponding archive mapping within existing authorization. Existing plans and archives keep their original mapping unless a separate authorized migration establishes ownership, checks collisions, preserves every byte, and verifies the result; never automatically adopt unscoped data from another project or rewrite an existing archive.

Confirm the exact project/worktree binding, storage scope, repository key when global, and effective memory-maintenance guidance. Reuse a plan name already supplied by the authorized task or available in current context; list only the selected repository's plan topics when name discovery is needed. Read an existing matching plan when its contents are needed and are not already current in context. A global listing may expose other repositories; visibility grants no authority to read or mutate them. Reuse only a plan for the same ongoing task; preserve unrelated plans and choose a distinct name on collision. Review the concrete plan before writing and confirm successful persistence before dependent work. Refresh the full stored content only when required to resolve an information gap, stale or invalidated context, a writer change, suspected concurrent change, conflict, uncertain operation, or explicit content-verification requirement. Missing required Memory capability, inaccessible required content, failed persistence, or failed required verification blocks dependent work; report the exact operation and preserve the last confirmed plan.

### Plan content

Keep one concise shared plan with the goal and acceptance conditions; Issue or user-request source; constraints and non-goals; verified project facts and exact source pointers; chosen direction and unresolved questions; bounded steps, dependencies, and verification approach; completed/current/remaining work; actual checks, blockers, and residual risks. Distinguish facts, assumptions, proposals, and accepted decisions. Use compact deltas and useful current evidence rather than transcripts, full diffs, logs, or private reasoning. Concision applies to new entries; it never permits replacing accumulated content with a current-state or final summary. Preserve existing goals, constraints, requirement changes, sourced facts, decision reasons, stage progress, shared contributions, failures, and verification records. Mark a stale conclusion as superseded, retaining its original claim and evidence and adding the replacement, reason, and source; do not silently delete or rewrite its history.

### Preservation checks for plan updates

1. For a preservation comparison or whole-document replacement, use a complete current plan as the baseline. It may be a complete read already held in current context for the same uninterrupted, parent-coordinated writer turn, combined with that writer's explicitly successful changes. Refresh the complete plan if the baseline is missing, stale, invalidated, or a writer handoff, suspected concurrent change, conflict, or uncertain result occurred. An outline or unconfirmed contribution is not a baseline.
2. Merge only authorized status/step changes and append new facts, results, or evidence. Prefer a precise local edit when its target is unambiguous; use literal matching with protection against unintended multiple matches. Before whole-document replacement, obtain the applicable complete baseline and submit the full merged document, never a newly drafted summary. Review the candidate against the baseline so every prior record, contribution, provenance, reason, and evidence remains traceable; apply the supersession rule above to changed conclusions.
3. A successful write/edit receipt confirms execution, not semantic correctness, content preservation, or concurrency control. In the same uninterrupted controlled writer turn, the confirmed change may be added to the held baseline without rereading the full plan after each update. Read back stored content when explicitly required, when actual stored-content acceptance is being performed, or when an error, conflict, invalidation, or uncertain result requires it. When triggered, compare the complete relevant content and confirm new entries separately; an ordinary successful write or a spot check is not a substitute for a required comparison.
4. Missing content, conflicting contributions, or uncertain write/read results block affected reporting, dependent actions, and archiving. Preserve the last confirmed baseline, refresh current state, and reconcile under existing authorization before rechecking. Never blindly replay a stale replacement. Keep comparisons within authorized context; do not persist transcripts or private reasoning.

### Update boundaries and dependent actions

Every participating Agent, including the parent and any verifier, uses the same current plan context when needed on entry/resume; refresh it when required content is absent or stale. Record material progress and sourced facts at applicable phase, handoff, pause, or completion boundaries. Batch related updates within a phase; ordinary progress reports and unrelated small facts do not independently trigger a write. A fact that changes authorization, scope, acceptance, direction, or a dependent action must be recorded and analyzed before that affected action. A successful update does not by itself require an immediate readback; follow the preservation and uncertainty triggers above.

For a changed user requirement, first record the new instruction and its source as pending analysis. Then analyze its impact on scope, dependencies, acceptance, and the proposed solution; persist the analysis and revised plan, confirm the write operation, and perform any content verification triggered by this owner before proceeding. Only afterward may the parent authorize affected changes or dispatch. If the change arrives in a child context, submit it within the child's permitted contribution and return it to the parent; the child cannot amend the Contract or release work. Keep unaffected authorized work available only when it does not depend on the pending change.

### Shared access and update coordination

The parent supplies the exact project root, Memory name, relevant source scope, and allowed contributions in every affected dispatch. Determine which read, contribution-return, or write operations each assigned role actually needs; a shared name does not establish cross-Session access. The parent may merge an explicitly authorized, concise contribution while acting as the current record writer. Do not require every contributor to have Memory write tools, and do not treat one Agent's successful call as proof of another Agent's access. Missing required read access blocks work that depends on the inaccessible plan; failed persistence or required verification blocks dependent work. Never use an unverified contribution or filesystem file as a substitute for required shared-plan evidence.

Serialize updates to the shared plan. The parent coordinates one current record writer at a time. Other roles may submit concise, sourced contributions within their released scope; this does not grant them permission to write or read other records. A writer may reuse its complete held baseline and its own confirmed updates during the same uninterrupted controlled turn. Refresh after writer handoff or on evidence of concurrent change, conflict, invalidation, or uncertain outcome. Do not assume atomic compare-and-swap or locks from a Memory tool. Pause affected reporting/actions when the current state cannot be established; reconcile under the parent's existing authorization and never blindly overwrite or retry a stale full document.

The plan is shared task context, not the live parent mode/count/allocation/epoch record, an execution memo, or a source of authorization. Do not store that live scheduling state in it. Plan read/write access grants no access to other Memories, source files, raw peer context, or new effects. Respect the Context Firewall and each role's released scope; return proposals through the parent. A verifier may update only its named plan contribution and remains read-only for implementation and Git. A false execution-memo flag does not waive shared task-plan updates.

### Completion and archive

Keep the plan active while the task is incomplete or blocked. After every applicable Acceptance criterion passes:

1. Apply the preservation checks above to the complete active plan: update only completion status/steps and append final results, Acceptance evidence, and remaining limitations. Retain the accumulated document; a final summary may be appended but must never replace it. Before archiving, satisfy the required full content-preservation check using the selected lifecycle tool's verified receipt or, when using native Memory operations, the necessary complete content comparison.
2. Retain this verified final active content as the archive baseline and confirm the matching archive target is absent. Archive only this completed task's plan by moving its namespace/name, without changing its content. A collision blocks the move; preserve both entries and report it.
3. Verify the archived content is identical to the final active baseline and confirm the archive exists and the active name is absent. Use a matching verified archive receipt when the configured lifecycle service provides one; otherwise perform the necessary complete archive read and comparison. A missing record, content difference, or update/archive/required-verification failure blocks completion; preserve the last confirmed state and resolve uncertain effects before proceeding.

Archived plans are instruction-level immutable: never edit, delete, rename, or replace an existing archive, including to repair a failed archive comparison; tool visibility does not technically enforce this rule. Report such a mismatch for a separate authorized recovery decision. Never archive an unrelated or incomplete plan.

### Preservation acceptance scenario

Use a new synthetic plan in an authorized test scope, never an existing user's plan. Include multiple stages, a goal and constraint, a sourced requirement change, a decision with its reason, another contributor's entry, a failed check and later passing check. Include small facts such as “two untracked-file manifests verified” and “no PR template found” so a short final summary cannot accidentally pass. Supersede one conclusion with a reason and source, complete through the checks above, then archive. Verify every original record remains traceable, the superseded claim and its replacement both remain, final results were appended, the archive equals the final active baseline, and the active name disappeared. Also review a summary-only candidate and an occupied archive target: neither may advance to a write/move that loses content or overwrites an archive. Report actual exercised checks separately from scenario review; this does not prove tool-enforced immutability or recover past losses.

## Codex CLI / ChatGPT Desktop optimizations

### Configured deterministic lifecycle tools

When the workflow MCP profile exposes an authorized, configured Serena backend, use `task_plan_update`, `task_plan_complete`, and `task_plan_archive` for plan mutations. Discovery alone is insufficient: confirm backend availability, the exact configured checkout, and the returned storage scope/repository mapping. For shared global storage, the operator explicitly constructs `SerenaMemoryStore(memory_manager, project_root, storage_scope="global")` from the actual Serena `MemoryManager`; the compatibility default remains `storage_scope="project"`. Explicit server injection or a trusted startup factory supplies that service. The global root must already exist; the service neither initializes it nor guesses its location. Do not invent a factory, load arbitrary code from a tool argument, install a dependency, or guess a `.serena` directory to make a call pass. The service does not automatically load or migrate Serena configuration.

Each request still supplies the exact service-bound checkout's absolute `project_root`; it cannot choose another repository or switch storage scope. Separately configured services for the main checkout and linked worktrees derive the same global repository identity, history, revision and replay scope. Inspect the returned scoped `memory_name` rather than rebuilding a bare name. Global history uses an explicit repository identity; legacy project history remains checkout-bound. The service checks repository identity again before global Memory effects and fails if it changed. Capability/receipt evidence does not authenticate the caller or grant access to other repositories. Git's common-directory semantics are documented in [git-rev-parse](https://git-scm.com/docs/git-rev-parse) and [repository layout](https://git-scm.com/docs/gitrepository-layout).

| Operation | Agent input and required result |
| --- | --- |
| `task_plan_update` | Submit only typed records with stable IDs, text and sources, the expected content revision, and an operation ID. Creation must explicitly expect absence. Adopt existing Markdown by retaining its opaque original content and appending typed records; declare goals and acceptance criteria rather than inferring them. A replacement references an existing record and supplies its reason; the old record remains. Never send a replacement document, free-form patch or regex. |
| `task_plan_complete` | Supply final results, limitations, the expected revision and operation ID, and evidence mapping every current declared criterion to passed verification records. Resolve blockers through appended records first. The service validates structure and preservation; it cannot prove the truth or semantic sufficiency of supplied evidence. |
| `task_plan_archive` | Supply the completed active plan identity and expected revision. The destination is the corresponding fixed archive namespace. Require an identical-content receipt and active-name absence; do not request reference propagation or arbitrary destination changes. |

Use each currently exposed payload schema for exact fields and bounds. The service performs the full baseline read, structured merge, preservation checks and readback internally; inspect its compact receipt for the matching project/plan, revision, state, replay and preservation result before relying on success. When that receipt verifies the requested operation and content-preservation result, do not repeat the same full readback through native Memory tools. A revision conflict requires reading and reviewing current state before a new request. Identical update/completion retries reuse the original operation ID and payload; a changed payload needs a new ID. Reconciliation-required or uncertain effects block dependent work; do not bypass a selected service's failure by invoking raw Memory writes. These deterministic operations make no model or network requests.

The adapter honors Serena memory access policies and operates on its actual canonical files. Its lock serializes cooperating lifecycle-tool calls; direct Serena tools and external writers do not automatically join that lock. Do not claim global compare-and-swap, raw-tool ACLs, or immutable archives against outside writes. Stronger enforcement requires the host to restrict those other write channels. Missing host enforcement does not establish an unavailable capability or prevent unrelated authorized work; report the precise protection boundary.

### Native Memory path

If no configured lifecycle service has been selected, use only the Serena operations actually exposed and authorized, with all general preservation and storage-scope checks above: `list_memories`, `read_memory`, `write_memory` or `edit_memory`, and a permitted archive operation. Confirm project activation, the actual global-root mapping when selected, the verified repository key, and exact schemas. List only the relevant plan topic when discovering a name. A normal successful write/edit result confirms execution and does not require an immediate full `read_memory`; refresh and compare stored content only at the triggers defined above. `write_memory` replaces the named content, so do not use it for an update without the applicable full baseline; prefer a precise authorized `edit_memory` for a bounded change. Filter any global listing to `global/token-io-decoupling/repos/<repository-id>/plans` or its corresponding archive topic. Supply logical names, never an absolute filesystem path as `memory_name`. If the current tools cannot establish the required identity or mapping, block the shared path; do not replace it with a worktree-local copy. Native `rename_memory` propagates `mem:` references, so establish that its effects remain authorized and the final content comparison can pass; otherwise stop that archive step. Never treat it as an atomic no-clobber primitive. Native `/plan`, local recall and chat compaction do not persist this shared record. One Session's successful calls do not prove another Agent's access; check each assigned Agent. [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp).

## Claude Code CLI / Claude Desktop optimizations

This repository's deterministic lifecycle MCP tools do not support this runtime; mark that optimization `Not applicable`, without inferring that its native MCP capability is absent. Use the same Serena MCP Memory service only when connected and actually exposed to that Agent, preserving the general checks and evidence above, including verified repository identity and scoped global names. Establish Git common-directory identity only through actually exposed, authorized local tools; do not infer it from a directory basename or select another repository's visible topic. Discover `list_memories`/`read_memory`, `write_memory` or `edit_memory`, and the permitted archive operation using exact project/name and current schemas. Read only when needed information is absent or stale; treat a successful write result as execution confirmation, not content, semantic, or concurrency verification. Filter global plan listings to the verified repository topic; absolute filesystem paths are not Memory names. Native `rename_memory` propagates `mem:` references: verify the effects are authorized and required content preservation can pass before use; otherwise block that step. Discovery, approval and availability may differ from Codex; do not assume identical prefixes or inherited connections. Native Plan mode, todo state and automatic memory are not substitutes. Missing required identity/mapping or denied permissions blocks dependent persistence/assignment, without falling back to a new local copy. Claude Desktop never uses GUI navigation to establish access. [Claude Code MCP tool availability](https://code.claude.com/docs/en/mcp#tool-availability).
