# Coding Workflow — Multi-Agent Mode

[English](coding-multi-agent.md) | [简体中文](coding-multi-agent_zh_cn.md)

This route is selected by the Coding workflow and is valid only after the Mode checkpoint releases Multi-Agent Coding. Before execution, the checkpoint composes the [mode-confirmation](../layer-01-fundamental-concepts/delegation-mode-confirmation.md), [count-gate](../layer-01-fundamental-concepts/delegation-mode-count-gate.md), [mode-reentry](../layer-01-fundamental-concepts/delegation-mode-reentry.md), [state-record](../layer-01-fundamental-concepts/delegation-state-record.md), [child-creation](../layer-01-fundamental-concepts/delegation-child-creation.md), [child-role-allocation](../layer-01-fundamental-concepts/delegation-child-role-allocation.md), [child-dispatch](../layer-01-fundamental-concepts/delegation-child-dispatch.md), [child-reuse/replacement](../layer-01-fundamental-concepts/delegation-child-reuse-replacement.md), and [child-lifecycle](../layer-01-fundamental-concepts/delegation-child-lifecycle.md) owners.

## Mode contract

- A Worker receives one released Interaction Slice and returns only through the parent-controlled channel; it never creates a recursive hierarchy or treats another Worker's progress as permission.
- The [mode-confirmation](../layer-01-fundamental-concepts/delegation-mode-confirmation.md), [count-gate](../layer-01-fundamental-concepts/delegation-mode-count-gate.md), [mode-reentry](../layer-01-fundamental-concepts/delegation-mode-reentry.md), and [state-record](../layer-01-fundamental-concepts/delegation-state-record.md) owners govern their respective root mode, count, re-entry, and state-record boundaries; [child-creation](../layer-01-fundamental-concepts/delegation-child-creation.md), [child-role-allocation](../layer-01-fundamental-concepts/delegation-child-role-allocation.md), [child-dispatch](../layer-01-fundamental-concepts/delegation-child-dispatch.md), [child-reuse/replacement](../layer-01-fundamental-concepts/delegation-child-reuse-replacement.md), and [child-lifecycle](../layer-01-fundamental-concepts/delegation-child-lifecycle.md) own their corresponding child boundaries. Role names do not independently authorize a Session.
- If the user forbids subagents, child tasks, independent Sessions, or parallel delegation, stop this route and return to route selection; do not simulate multi-agent behavior.

Compose [shared protocols](../../share/shared-protocols.md), [delegation state](../layer-01-fundamental-concepts/delegation-state-record.md), [the mode-confirmation reference](../layer-01-fundamental-concepts/delegation-mode-confirmation.md), [the mode/count gate](../layer-01-fundamental-concepts/delegation-mode-count-gate.md), [the mode-reentry reference](../layer-01-fundamental-concepts/delegation-mode-reentry.md), [child creation](../layer-01-fundamental-concepts/delegation-child-creation.md), [child role allocation](../layer-01-fundamental-concepts/delegation-child-role-allocation.md), [child dispatch](../layer-01-fundamental-concepts/delegation-child-dispatch.md), [child reuse/replacement](../layer-01-fundamental-concepts/delegation-child-reuse-replacement.md), [child lifecycle](../layer-01-fundamental-concepts/delegation-child-lifecycle.md), [session model](../layer-01-fundamental-concepts/session-model.md), [session role ownership](../layer-01-fundamental-concepts/session-role-ownership.md), [session context firewall](../layer-01-fundamental-concepts/session-context-firewall.md), and [execution control](../layer-01-fundamental-concepts/execution-control.md) for this route; load [context exchange](../layer-01-fundamental-concepts/context-exchange.md), [context workspace boundary](../layer-01-fundamental-concepts/context-exchange-workspace-boundary.md), [context handoff](../layer-01-fundamental-concepts/context-exchange-handoff.md), or [content memo](../layer-01-fundamental-concepts/content-memo.md) only when the released slice needs them. The Mode checkpoint has already validated the record; the checkpoint list below is the complete route composition.

## Responsibility boundary

Use the role ownership defined in [session role ownership](../layer-01-fundamental-concepts/session-role-ownership.md); this route adds only the Multi-Agent conditions below.

## Route-specific environment requirements

Use the inventory and shared runtime rules from the [Environment capability inventory](../layer-02-workflow-concepts/environment-capability-inventory.md), including the model bindings in [Runtime and Model Provider Support](../layer-01-fundamental-concepts/runtime-provider-support.md). Continue only when it exposes the capabilities required by the task record and released slice. A Worker returns only to its direct parent and cannot create/manage Agents or contact arbitrary threads.

## Ordered route checklist

Run every numbered stage in order. For every linked owner, check its applicable actions and pass condition, record the result and evidence, and stop when a required result is missing. Record `Not applicable` with a reason for each conditional action; a link or earlier summary is not proof that its check was completed. The Coding selector completed stages 1–3 before route entry: inspect their released evidence without repeating the gates. The root parent makes semantic decisions and controls every release; Workers return only through that parent.

1. **Contract and common protocol.** Confirm the [Contract checkpoint](../layer-02-workflow-concepts/contract.md) has an explicit goal, hard user/runtime/repository/permission/safety limits, authorized effects, settled decisions, open questions, and acceptance conditions. Apply the [shared protocols](../../share/shared-protocols.md): keep one current Semantic Contract, separate observed facts from assumptions, send bounded amendments with a stable prefix and small delta, use a parent-only return path and a short Dispatch Preview, and stop the dependent slice if required context or a return path is unavailable. Do not turn an unresolved question into dispatch authority.
2. **Environment and capabilities.** Confirm the [Environment checkpoint](../layer-02-workflow-concepts/environment.md) classified exactly one runtime from explicit metadata, using tools and workspace facts only as corroboration; do not use a browser, GUI, or visual content to identify the runtime. If classification is ambiguous, use the provider owner's exact fallback question and pause. Check the [Environment capability inventory](../layer-02-workflow-concepts/environment-capability-inventory.md) for actual models, profile-required parameters, child identity, parent-controlled return path, bounded wait, lifecycle, filesystem/permission scope, and tools. Apply [Runtime and Model Provider Support](../layer-01-fundamental-concepts/runtime-provider-support.md) for branch-specific model bindings. Record missing or unknown requirements in `unavailable_capabilities`; block dependent work instead of inferring or substituting a capability.
3. **Mode, count, and record.** Confirm the [Mode checkpoint](../layer-02-workflow-concepts/mode.md) released exactly `Multi-Agent Coding`. Check [mode confirmation](../layer-01-fundamental-concepts/delegation-mode-confirmation.md), [count gate](../layer-01-fundamental-concepts/delegation-mode-count-gate.md), [state record](../layer-01-fundamental-concepts/delegation-state-record.md), and [mode re-entry](../layer-01-fundamental-concepts/delegation-mode-reentry.md): the conversation mode and positive count were explicitly selected or defaulted after 15 seconds and then locked; `gate_status: released`; exactly `child_count` locked planned allocations have role, slice, scope, mutations, return conditions, lifecycle, and explicit `write_content_memo`. Later directives in this conversation reuse the locked mode/count; a conflicting topology blocks dependent work until a new conversation. A prohibition, absent record, or unavailable capability blocks this route; never silently change mode or count.
4. **Session roles and Context Firewall.** Check the [session model](../layer-01-fundamental-concepts/session-model.md) and [role ownership](../layer-01-fundamental-concepts/session-role-ownership.md): the root parent directly analyzes instructions, project environment, and code details needed to define each child task, owns the Contract/decisions/acceptance, and releases precise scopes. The assigned Primary Session owns implementation; an allocated verifier owns read-only independent checking; the docs/Git role owns only its separately released work. An unallocated role is not an independent Session. Apply the [Context Firewall](../layer-01-fundamental-concepts/session-context-firewall.md): parent reconnaissance is bounded, Workers consume only released raw state, and returns are compressed facts with source pointers.
5. **Allocation and child budget.** Under [child role allocation](../layer-01-fundamental-concepts/delegation-child-role-allocation.md), confirm every independent role consumes one locked slot and no unallocated verifier or auxiliary role is invented. Allocate Context Bootstrap/Refresh only for at least two independent downstream Workers, broad discovery with at least three routed policy modules, or roughly more than 20k source characters / 5k token-equivalents. Skip it for one small Worker or a documentation-only fast path; record the reason. Do not create a child yet: first confirm the relevant facts, context, decision, and released slice in stages 6–8.
6. **Context and transport.** At [Context](../layer-02-workflow-concepts/context.md), name the smallest next-slice question, read only required sources, and check reused context's owner, source paths, freshness, and epoch. If Workers need file-backed exchange, apply [context exchange](../layer-01-fundamental-concepts/context-exchange.md): pass only neutral facts, exact pointers, hashes, and freshness data; a bootstrap capsule uses `MANIFEST.md`, `project-context.md`, and `policy-context.md`; prefer authoritative sources, check HEAD/tree, tracked deltas, listed source hashes, relevant untracked state, and task/scope freshness; reject stale capsules, and never use a capsule as the Contract or verification. Apply [context workspace boundary](../layer-01-fundamental-concepts/context-exchange-workspace-boundary.md): parent sets `CONTEXT_ROOT=<primary-worktree>/.token-io-decoupling/context/`, keeps its `INDEX.md` parent-owned and the runtime directory ignored by Git, provisions each named Worker directory and read-only import, enforces RW/RO/DENY paths with real isolation, and stops if the boundary cannot be enforced; a separate worktree alone is not isolation. Apply [context handoff](../layer-01-fundamental-concepts/context-exchange-handoff.md) only for a concrete handoff or recovery: record achieved state, failed approaches with evidence, current changes and verification, blockers, and the next useful action; update the local/root indexes, expose only named predecessor documents, and preserve the predecessor directory. If no exchange or handoff is needed, record each omission separately.
7. **Decision and two-level plan.** At [Decision](../layer-02-workflow-concepts/decision.md), state the material question, facts, constraints, options, chosen direction, rejected alternatives, authorized paths/mutations, and unreleased boundary. Apply the [decision gate](../layer-01-fundamental-concepts/execution-decision-gate.md): prepare a concise Decision Brief with Problem, Known facts, Assumptions and unknowns, Decision questions, Solution envelope, Risks, Acceptance, and Stages/checkpoints unless its simple fast path applies; release reconnaissance only while a material choice remains open. Use [execution planning](../layer-01-fundamental-concepts/execution-planning.md) to order bounded inspection, implementation, and focused checks with expected evidence. Confirm the Contract permits one concrete slice before any child assignment or material dispatch.
8. **Slice and stage release.** Use [execution control](../layer-01-fundamental-concepts/execution-control.md) to state `Objective`, `Authorized scope/mutations`, `Return conditions`, and `Unreleased boundary`; keep dependent writes sequential. Apply [execution stage feedback](../layer-01-fundamental-concepts/execution-stage-feedback.md) for high-uncertainty work: predeclare short evidence-producing stages, keep routine mechanics inside a stage, and return compressed Progress Signals only at material boundaries. Route a new semantic choice back to stage 7.
9. **Child creation and lifecycle.** Under [child creation](../layer-01-fundamental-concepts/delegation-child-creation.md), confirm the current runtime's real parent-controlled child mechanism, the released record, locked count, planned slot, role, slice, allowed paths, return conditions, and required context before creating exactly the authorized child. Resolve any provider-specific operation in the linked Layer-01 owner. Record the child's actual identity/lifecycle in the planned allocation. Apply [child lifecycle](../layer-01-fundamental-concepts/delegation-child-lifecycle.md): keep created children identifiable and their lifecycle persistent in the parent record; do not clean up a durable task-panel entry merely because work finished; wait or send only authorized input while pending/running, mark completed only after final evidence, and retain error/interruption state. Never create an extra child to recover from an error.
10. **Dispatch, Worker record, and memo.** Apply [child dispatch](../layer-01-fundamental-concepts/delegation-child-dispatch.md): parent confirms prerequisite facts, sends a concise Dispatch Preview of about 1–3 lines and 80 tokens, names only allowed code/context paths, and releases one slice unless independent non-conflicting work was approved. Under [Worker boundary](../layer-01-fundamental-concepts/delegation-worker-boundary.md), pass only the relevant released record snapshot; Workers do not mutate it, reopen gates, coordinate peers, or create children; block dispatch if the record cannot be persisted or returned. Apply [content memo dispatch](../layer-01-fundamental-concepts/content-memo-dispatch.md): serialize explicit `write_content_memo: true | false` in every released bundle. If enabled, apply the [content memo contract](../layer-01-fundamental-concepts/content-memo.md) and [memo lifecycle](../layer-01-fundamental-concepts/content-memo-lifecycle.md): Chinese Worker prose in `content-memo.md` or a named equivalent, stable facts/evidence/changed paths only, updates at material milestones, and discoverability in the Worker index; no secrets, raw logs, complete diffs, or per-command journal. If disabled, record the parent reason; do not create a no-op Worker for an inapplicable role.
11. **Implementation and Control.** At [Implementation](../layer-02-workflow-concepts/implementation.md), require the Worker to re-read the released objective/scope/return conditions, inspect only needed files, make the smallest authorized change, run focused provisional checks without treating them as final acceptance, and return changed paths, evidence, issues, and the unreleased boundary. At [Control](../layer-02-workflow-concepts/control.md), parent records `Status`, `Findings`, `Changed`, `Verification`, `Issue`, `Need`, and `Unreleased boundary`, checks material risks/scope/effects, and explicitly chooses Continue, Amend, Stop, or Evidence-on-Demand. Apply [child reuse/replacement](../layer-01-fundamental-concepts/delegation-child-reuse-replacement.md): reuse the same child for authorized follow-ups; after count locking, a failed child cannot be replaced. Repeat stages 6–11 only for another approved slice.
12. **Final-state verification.** At [Verification](../layer-02-workflow-concepts/verification.md), capture the current fingerprint and acceptance conditions, then run applicable holistic and targeted checks against that state. Apply [Verification independence](../layer-02-workflow-concepts/verification-independence.md): use an allocated independent verifier when required, otherwise label same-Session checks as logical and independence unavailable. Apply [Verification reporting](../layer-02-workflow-concepts/verification-reporting.md): record passed, failed, unavailable, assumed, residual risks, unresolved items, and blocking effects. Apply [Verification epoch](../layer-02-workflow-concepts/verification-epoch.md): track implementation/content, documentation, and Git metadata separately; re-evaluate changed coverage with current evidence, reusing the allocated verifier for later epochs. Do not release dependent work while a required evidence gap remains.
13. **Repair and re-verification.** At [Repair](../layer-02-workflow-concepts/repair.md), name failing evidence, affected paths, and the smallest candidate. Use the [Repair scope gate](../layer-02-workflow-concepts/repair-scope-gate.md) to confirm Contract/Decision compatibility; return to stages 1 and 7 if a material decision changes. At [Repair execution](../layer-02-workflow-concepts/repair-execution.md), release only an authorized narrow repair to the existing child and run focused checks. Under [Repair verification handoff](../layer-02-workflow-concepts/repair-verification-handoff.md), capture the new state and return to stage 12, preferably to the same allocated verifier. Apply the lifecycle/reuse boundary on interruption; if the child cannot safely continue after count locking, mark the route blocked rather than replace it. If no failure exists, record Repair as not applicable.
14. **Documentation.** At [Documentation](../layer-02-workflow-concepts/documentation.md), confirm approved paths, audience, purpose, source evidence, and the verification boundary; release documentation/comments as a bounded scope separate from Git. Synchronize maintained language mirrors, advance the documentation epoch, and run applicable Markdown, link, whitespace, multilingual, and scope checks. If content changes behavior, the Contract, or acceptance, return to implementation/content Verification; otherwise retain valid product evidence. Report unavailable checks.
15. **Git effects.** At [Git](../layer-02-workflow-concepts/git.md), confirm exact repository, worktree, branch/ref, remote, operation, and authorization. Inspect status/history, preserve unrelated changes, and confirm staged/committed content matches the latest verified content and documentation fingerprints. Treat index/commit/branch/history changes as Git metadata changes; separately authorize commit, push, Issue, PR, and other effects. Stop on ambiguous target, conflict, missing permission, or unverified content. If no Git work applies, record why.
16. **Acceptance.** At [Acceptance](../layer-02-workflow-concepts/acceptance.md), map every Contract criterion to current evidence for the latest implementation/content, documentation, and Git metadata epochs. Check paths/effects against scope; report passed, failed, not-run, unavailable, assumed, and user-authorized items separately with residual risks. Distinguish true independent Sessions from same-Session phases and report `COMPLETE` only when every required item and boundary is resolved.

For each released Worker bundle in stages 8–10, make these fields explicit:

```text
Owner: Primary Output | Documentation/Comments & Git Operations | Change Verification
Objective: ...
Authorized scope/mutations: ...
write_content_memo: true | false
Return conditions: ...
Unreleased boundary: ...
```

## Completion

Apply the root Coding completion gate for documentation, Git, and final acceptance. The final report must distinguish real independent Sessions from same-Session logical phases and map every acceptance criterion to current evidence.
